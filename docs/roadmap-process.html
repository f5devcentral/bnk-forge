The pipeline

  1. Decide → ADR. Any architecture decision becomes an ADR: docs/adr/D-0XX-title.md (or inline in .agent/DECISIONS.md for legacy D-001–D-004). Status: Proposed → Accepted → (Superseded). One decision = one ADR.
  2. Slice into GitHub issues. When an ADR has buildable work, create issue(s) — one per epic, or a tracking issue plus per-slice issues for multi-PR epics. Label enhancement plus a theme label (e.g. dynamic-by-default). The body links its ADR and the roadmap. GitHub issues are the cross-clone source of truth for completion — the .agent/ framework is local and git-ignored, so it cannot be the shared record.
  3. Add to the roadmap. Place the item in docs/ROADMAP.md (correct section plus the issue index), then regenerate docs/roadmap.html. docs/ROADMAP.md is the shared "what's next"; .agent/backlog/BACKLOG.md is the local agent queue and points here.
  4. Build → PR → staging. PRs target staging (review-gated). Reference the issue in the PR body. Note: staging is non-default, so Closes #N does not auto-fire.
  5. Close + update status. On merge, close the issue with a comment citing the PR (manually, bin/maf-gh.sh issue close … --as-role lead --confirm-write --reason "…", or the auto-close Action once #185 ships). Flip the roadmap status to shipped. A partial epic gets a progress comment and stays open — never close an epic for a single slice.
  6. Regenerate the views. docs/roadmap.html and this page are generated from the markdown; refresh them whenever the roadmap changes.
Agents — answering "what's next?"  Read docs/ROADMAP.md section 1 (or open roadmap.html). Take the highest-priority unblocked item with an open issue. Discover a new bug or idea mid-work? File an issue and add it to the roadmap — never leave an orphan TODO. Verify "remaining" against current staging first; memos and the roadmap can lag recent merges.
