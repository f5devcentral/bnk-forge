BNK Forge · Quality

E2E Testing Personas & Workflows

Six personas that drive end-to-end testing of BNK Forge. Each owns one stage of the Day‑0 → Day‑1 → Day‑2 lifecycle for F5 BIG‑IP Next for Kubernetes — and one isn't human at all: an AI agent driving Forge through MCP/API. Each has a golden path (happy-path smoke test) and rough-edge probes (negative paths that surface the bugs real users hit). Grounded in the 461-feature audit, the 150-tool MCP catalog, the real app navigation, and the existing scripts/e2e/ harness.

Real humans don't move in a straight line. Golden paths here are not a single forward march — they include what people actually do mid-flow: hit Cancel, refresh, click browser Back/Forward, navigate away and come back, open a second tab, bookmark/deep-link a screen, double-click a button, or let a session idle out. Each persona weaves in the relevant ones, and the shared cross-cutting interaction probes apply to all.

Day‑0/1 · Build (cloud + on-prem) Day‑2 · Traffic Day‑2 · Operate Validate Govern AI Agent · MCP/API

The friction real users feel clusters around the handoffs between roles — the infra person hands a running cluster to the network person, who hands traffic config to ops. Each persona owns one stage, and the seams between them are where bugs hide. Known weak spots from the audit (23 Blocked, 2 Error, 1 Partial) are tagged against the persona that trips on them.

01
Day‑0/Day‑1 · Infrastructure Builders

Priya & Raj — Infrastructure Builders (cloud / on-prem)

One role, two environments. Priya stands infra up in the cloud; Raj stands it up on-prem (DPU / bare-metal). Same job, same handoff: both produce a running, licensed BNK cluster they then hand off to the Day‑2 personas (Marcus for traffic, Sofia for ops). Testing them together keeps the cloud (Terraform/OpenTofu) engine path and the on-prem (SSH) engine path honest against the same downstream contract — whatever they hand off must look identical to operate against.

"Give me a working, licensed BNK cluster — from a blueprint in my cloud, or over SSH on my own hardware — without hand-wiring it, and hand it off clean."

1a · Priya — Cloud. Fresh AWS account (SSO), no clusters yet. First-time-user energy, evaluating whether Forge beats her own scripts.

✓ Golden path (cloud) — primary smoke test
  1. Login → Auth Templates: create AWS Credential Template, mark default.
  2. Cloud Credentials: SSO device-code login → acquire temp creds → account/region appear.
  3. Catalog → Blueprints (or Stacks): pick EKS+BNK blueprint, read modules.
  4. Projects → Create: instantiate blueprint; fill vars + secrets; resolve missing: modules.
  5. Deploy-all: Orchestration chain advances (eks-create → cneinstall → ready-gate → license-gate).
  6. Licensing: License CR activates → BNK Active.
  7. Handoff to Marcus/Sofia; later teardown → orphan-free (reverse-DAG destroy).
⚡ Probes (cloud)
  • Missing required variable → UI blocks clearly, not a mid-chain failure.
  • AWS creds expire mid-deploy → friendly 401 + stale-badge clears, not a 500 wall (regression-guard).
  • Module fails then retries → chain keeps auto-advancing? (D‑031 #320)
  • AKS/GKE instead of EKS → documents the token-injection gap (#218).
  • Destroy halts at FLO on a stale token → force-destroy / fail-soft works.

1b · Raj — On-Prem / DPU & Bare-Metal. Owns physical hosts + BlueField DPUs in his own DC. No cloud console — SSH + PXE/BFB images. DPU is the largest single surface (33 features) and least-mature; exercises the SSH engine, not Terraform.

✓ Golden path (on-prem)
  1. SSH Credentials: register jumphost + key (auto-bootstrap), Test connection, probe kubeconfig over SSH.
  2. Infrastructure → Bare-Metal Hosts: register host; BlueField Images: upload/select a BFB.
  3. Catalog: pick the SSH/DPU BNK blueprint; resolve bare-metal version profile.
  4. Projects → Create + Deploy: SSH-deploy BNK layer (scaffolding → manifest/helm → cneinstance → VLANs/gatewayclass).
  5. Licensing: BNK Active on the DPU.
  6. Handoff to Day‑2; destroy cleanly (e2e on dpu-server).
⚡ Probes (on-prem)
  • SSH connection test / key bootstrap on wrong port/host → clear error (these are Blocked audit items).
  • Probe kubeconfig via SSH against a host with no cluster → graceful, no hang.
  • SSH command mid-deploy drops connection → retried/resumed, not silently stuck.
  • Handoff contract matches Priya's — a cluster Sofia operates looks the same whether built in cloud or on-prem.
↺ Interaction (non-linear) — the deploy is long, nobody just watches
  • Refresh the browser mid-deploy → Orchestration progress resumes live, not lost / not stuck "pending".
  • Navigate away to Dashboard and back → progress still there and accurate.
  • Cancel a deploy in flight → it stops and leaves no orphaned cloud resources / no half-locked modules.
  • Cancel the Create-Project wizard halfway → no partial project / orphaned vars.
  • Browser Back out of the variable form → re-entry preserves values (or warns), doesn't silently drop them.
  • Double-click Deploy-all → exactly one deploy starts (idempotent submit).
  • Deep-link / refresh on /projects/:id/:section → loads directly, no SPA 404.
  • On-prem: cancel a Test-connection / BFB upload → no stuck spinner, no half-uploaded image; refresh during SSH deploy resumes step progress.

Weak spots: Cloud Credentials SSO/IAM (Blocked); Deploy Module full chain + OpenTofu Apply (Error); all 7 Licensing (Blocked); SSH test/bootstrap/command/probe (Blocked); SSH-BNK-layer ports in progress (#204/#205/#210).

Day‑2 · Traffic

Marcus — NetOps / Application Delivery Engineer

Profile. Owns north-south traffic. Knows F5 classic (TMOS/AS3), VIPs, iRules, CIS. Inherits Priya's running cluster and must make it serve traffic — and migrate the existing F5 estate onto BNK.

Environment. Licensed BNK cluster + an existing classic BIG-IP and/or CIS-managed Ingress.

"Configure CNFs/gateways on BNK, and migrate my existing proxies/CIS config onto it without rebuilding by hand."
✓ Golden path
  1. F5 BNK: view licensed instance, health, version.
  2. CNF (CRD dashboard): browse live CRs; inspect GatewayClass / VLAN / listener.
  3. Discovery: point at existing classic BIG-IP / CIS → inventory VIPs, AS3, Ingress.
  4. Migrate (D‑021/D‑023): classify objects (migratable / BNK-native / unsupported) → generate BNK CRs → review diff.
  5. Apply config → CRs reconcile, traffic path comes up.
  6. Connectivity: verify data-plane end-to-end.
⚡ Rough-edge probes
  • CRD write path ("CRD Wizard", D‑018 P3) Blocked on authz/audit → writes gated, not silently dropped.
  • CIS IngressClass kind-aware classify (#295) → edge cases (IngressLink, OpenShift Route, ConfigMap AS3) land in the right bucket.
  • Discovery against unreachable / wrong-cred device → clear error vs hang.
  • Migrate an unsupported object type → warns, doesn't emit a broken CR.
↺ Interaction (non-linear)
  • Refresh the CNF/CRD dashboard → live CR list reloads from the cluster, not a stale snapshot.
  • Cancel a discovery scan in flight → stops; partial results discarded or clearly marked partial.
  • Back out of the migration review/diff → returns to classification without losing the generated plan.
  • Change screens (BNK → CNF → Discovery) and back → each view re-orients; no leftover selection.

Weak spots: CNF write path (Blocked); AS3/CIS coverage edges; SSH Connection/Command (Blocked).

03
Day‑2 · Operate (on-call)

Sofia — SRE / Platform Operations

Profile. Owns fleet health at 3am. Doesn't deploy new things; she watches, upgrades, recovers. Judges the product by how fast it tells her what's wrong and what to do.

Environment. Several running projects/clusters across clouds.

"Tell me what's drifting or unhealthy, let me upgrade safely, and let me recover a failed module without nuking the cluster."
✓ Golden path
  1. Dashboard: scan fleet health, recent deploys, alerts.
  2. Fleet → cluster + Operators tab → health.
  3. Alerts: configure Slack/webhook → Test → confirm delivery + history.
  4. Drift: detect drift → review → reconcile.
  5. BNK Upgrade: plan (registry-driven GA) → run → handle supersede/cancel.
  6. Tasks / Orchestration: open failed task → logs → retry just that module.
  7. Snapshots / Backup / QKView: snapshot before upgrade; pull QKView for support.
⚡ Rough-edge probes
  • Upgrade with undecodable FLO secret → graceful handling (#284), not a crash.
  • Two upgrades on same entity → supersede / 409 behaves.
  • Alembic schema drift at deploy (#161) → fails loud, doesn't silently corrupt.
  • Dead webhook URL → failure recorded + rate-limited, not retried into oblivion.
  • Notifications stay bell-only / zero-toast (D‑027).
  • Retry a mid-chain failure → event-chain resumes.
↺ Interaction (non-linear) — on-call, jumping between screens fast
  • Cancel an upgrade in flight → stops safely; supersede/cancel UX is honest about final state (#284).
  • Refresh during drift reconcile → progress preserved, doesn't double-apply.
  • Navigate away from a running task and back → live logs/status reconnect, not frozen.
  • Two tabs on the same project / alert channel → edits don't clobber; conflict surfaces.
  • Bell notification deep-links to the right entity even after refresh / on a fresh session.
  • Session idles out while reading the dashboard → next action re-auths gracefully (no data loss, no white screen).

Weak spots: Licensing renew/switch (Blocked); QKView; drift reconcile.

04
Validate

Dev/QA — Performance & Validation Engineer

Profile. Runs load against deployed BNK to validate SLOs and compare releases. Cares about reproducibility and clean comparisons.

Environment. Running BNK target + one or more benchmark agent hosts (built-in or remote).

"Register a target and an agent, run a scenario, and compare two runs to see if a release regressed."
✓ Golden path
  1. Benchmarks → Targets: register a BNK target.
  2. Agents: built-in agent, or register + SSH-provision a remote agent host.
  3. Configs: create/select a scenario config.
  4. Runs: launch → watch live progress → completes + persists.
  5. Run Detail / Group View: inspect results.
  6. Compare: diff two runs / a run group → spot regression.
⚡ Rough-edge probes
  • Scenario override guard (#282) → injected override that should be rejected, is.
  • Remote agent auth flag (#286 Slice‑4) → unauthenticated agent call refused.
  • Agent host goes away mid-run → run marked failed cleanly, not stuck "running".
  • Compare runs with mismatched configs → warns, doesn't silently mislead.
↺ Interaction (non-linear)
  • Stop/cancel a run in progress → stops cleanly; partial results saved-or-discarded clearly (no zombie "running").
  • Refresh during a live run → progress + live metrics resume, don't reset.
  • Navigate away and back mid-run → reconnects to the same run, no duplicate.
  • Back out of the New-Run wizard → entered config preserved or clearly discarded.

Weak spots: Performance Testing edge; remote agent provisioning over SSH (Blocked).

05
Govern · Multi-env · Reporting

Aisha — Platform Admin / Team Lead

Profile. Owns who can do what and how config moves between environments. Manager-adjacent; wants a clean read-only story for reporting up. Security- and audit-minded.

Environment. Team of operators/viewers, a dev and a prod Forge, shared module sources / private registry.

"Manage users and roles, govern where modules come from, promote config dev→prod, and prove who did what."
✓ Golden path
  1. Users: create operator + viewer (role validation, must_change_password); confirm RBAC scoping.
  2. Credential Templates: central provider creds; mark defaults; Test template.
  3. Module Sources / Registry / Git VCS: register a Git source → sync → modules appear in Catalog.
  4. Config Export / Promotion: export project config from dev → import/promote to prod.
  5. Audit: filter/search log (user/action/resource) → export stats.
  6. MCP: MCP service account exposes fleet state (non-human, survives admin rotation).
⚡ Rough-edge probes
  • Viewer tries a write → forbidden, audited (RBAC enforcement).
  • Admin self-demotion / self-delete → blocked (FEAT‑0016/0018).
  • Audit search hits the details column (FEAT‑0014 was a real bug; WO‑4 #357) — regression-guard.
  • Test Credential Template → currently Blocked; document expected behavior.
  • Promote config where target env is missing a referenced secret/module → clear failure, not half-applied.
  • GitLab token metadata normalization (the one Partial feature) → feed a GitLab PAT, check normalization.
↺ Interaction (non-linear)
  • Cancel the Create-User dialog → no half-created user; Back out of an edit → no partial role change.
  • Cancel a module-source sync in flight → stops; Catalog not left half-populated.
  • Refresh the audit log with filters applied → filters + page persist (or are in the URL), not reset.
  • Paginate / change filters then Back → returns to the prior result set, not page 1.
  • Two admins editing the same user in two tabs → conflict surfaces, not silent last-write-wins.

Weak spots: Test Credential Template + SSO refresh for template (Blocked); config-promotion gaps.

06
Drive · Headless · MCP / API

Atlas — Autonomous AI Agent

Profile. Not a human. An LLM agent (Claude over MCP, or a CI/automation bot over REST) handed a scoped task — "stand up a dev cluster," "check fleet health and remediate drift," "run the nightly benchmark and report" — that drives Forge to completion through tools, no UI. It judges the product by whether tool contracts are truthful, errors are machine-recoverable, and risky operations are gated so it can't do damage by accident.

Environment. The MCP server — 150 catalogued tools (iac_operations 42, cluster_management 36, bnk_operations 19, diagnostics_fleet 19, cloud_auth 13, helm 11, system 6, config 4), risk-classed read_only 81 / mutating 53 / destructive 16, each with an auth_expectation and a truthful output contract — plus the REST API and the dedicated non-human mcp service account (PR #214, survives admin rotation).

"Hand me a scoped task and let me drive Forge to completion through tools — with truthful results, recoverable errors, and guardrails on destructive actions."
✓ Golden path
  1. Authenticate as the mcp service account (non-human; survives admin password rotation).
  2. Discover the tool catalog → names, risk classes, auth_expectations.
  3. Orient with read-only tools (system_health, fleet_health, list clusters/projects).
  4. Execute the allocated task via mutating tools (e.g. create_project → deploy → poll /orchestration/{run_handle}).
  5. Parse normalized envelopes — nested project/cluster objects; success from outcome, not HTTP 2xx (D‑017).
  6. On failure, consume the structured error envelope (failure_class) → retry / recover / escalate.
  7. Report / hand off the result to the human or next agent.
⚡ Rough-edge probes — the bug-surfacing gold for agents
  • Destructive-tool guardrail — a destructive tool (e.g. delete_cluster; 16 exist) needs explicit confirmation / elevated auth; agent can't nuke by accident.
  • auth_expectation enforced — a cluster_owner tool called by a non-owner is refused, not silently executed.
  • Truthful output contract — every envelope matches the catalog (the test_tool_output_contracts guarantee); no field drift.
  • Structured error envelope — failures return a machine-parseable failure_class, not raw 500 / HTML.
  • Outcome-derived success (D‑017) — never false-reports success on a 2xx that didn't actually license/deploy.
  • Admin rotation doesn't break MCP auth (PR #214) — long-running agent survives.
  • Deprecated → replacement_tool pointer honored — agent isn't stranded on a dead tool.
  • Long-poll orchestration — polls /orchestration/{run_handle} (real int id, not the dead D‑031 endpoint) to terminal state without hanging.
  • Idempotency — a retried create yields 409 / supersede, not a duplicate (module locking Phase 1.6).
↺ Interaction (non-linear / programmatic) — the agent's "cancel / refresh / come back"
  • Cancel a long operation via API/tool mid-flight → stops, reports a clean terminal state.
  • Resume after disconnect → agent reconnects, re-polls /orchestration/{run_handle}, picks up the same run.
  • Two agents (or agent + human in UI) on the same project → locking arbitrates; loser gets a clear conflict, not corruption.
  • Token expires mid-task → tool returns a structured auth error the agent can recover from, not an opaque hang.

Weak spots: cloud_auth tools (13) lean on SSO/IAM (Blocked); destructive-tool confirmation semantics; envelope drift vs catalog; MCP write path overlapping Blocked CRD-write authz.

Cross-cutting: real-human interaction probes

These apply to every persona (and, in programmatic form, to Atlas). Real users interrupt, back out, refresh, and multitask — so each golden path should run with these layered on, not as a clean forward march. A reusable checklist the per-persona tests inherit.

⛔ Interruption & abort

  • Cancel any long op (deploy, upgrade, discovery, benchmark, sync, upload) → actually stops, honest terminal state, no orphans / no half-locked modules.
  • Cancel a dialog/wizard half-filled → no partial writes.
  • Double-click a primary action → exactly one operation runs.
  • Abort then retry → retry works, no collision with the aborted one.

↺ Navigation (never one-way)

  • Refresh (F5) on any screen — incl. mid-op — recovers live state, no reset/stale.
  • Refresh on a deep route (/projects/:id/:section, /catalog?tab=…) → loads directly, no SPA 404.
  • Back / Forward through a flow → preserves data (or warns), never corrupts.
  • Navigate away mid-op and return → progress/logs reconnect, accurate.
  • Change screens repeatedly → each re-orients; no stale filter/selection bleed.
  • Bookmark / deep-link / share a URL → opens to the right place.

⚷ Concurrency & sessions

  • Two tabs / two users on one entity → conflict surfaces, not silent last-write-wins.
  • Session idle / token expiry mid-flow → graceful re-auth, no data loss, no white screen.
  • Admin credential rotation while others active → live sessions / MCP agents survive or re-auth cleanly (PR #214).

▦ State rendering (every screen owes you three)

  • Empty state renders intentionally — not blank / spinner-forever.
  • Loading state → skeleton/spinner, no flash of "nothing here".
  • Error state → shared ErrorState + retry, not a raw 500 (D‑025/D‑027).
  • Stale-after-action → list/detail reflects a mutation without a manual hard refresh.

Test-design note. Cheapest coverage = bake these in as decorators over each persona's golden path (run-step → refresh → assert; run-step → cancel → assert clean), not longhand per persona. Many are pure Tier‑1 (no cloud spend).

How to operationalize this for e2e

Priority order for a fast regression gate (cheapest signal first)
  1. Atlas MCP contract tests — tool-output contracts + risk/auth guardrails against a seeded Forge. Cheapest signal, no cloud, and they guard the agent path and the API every other persona rides on.
  2. Priya golden path (deploy → license → Active → teardown) — the keystone; harness exists in scripts/e2e/.
  3. Sofia alerts + drift + retry-resume — pure Day‑2, no cloud spend for the UI/API layer.
  4. Aisha RBAC + audit + module-source sync — fully mockable, no cloud; cheap governance guard.
  5. Marcus discovery/migrate — needs a target device or fixture.
  6. Raj on-prem/DPU build — needs an SSH-reachable host (dpu-server).
  7. Dev/QA benchmarks — needs a live target.
Two-tier design (so it stays a "quick check")

Tier 1 — no real spend

Atlas MCP/API contract + guardrail tests, plus Sofia & Aisha e2e, against a seeded Forge. Runs on every PR.

Tier 2 — real cloud / real hardware

Priya (live AWS) + Raj (SSH host) + Marcus/Dev‑QA against real targets. Nightly / pre-release. Uses the existing .github/workflows/e2e-tests.yml chassis.

Each rough-edge probe is a negative-path test — those surface bugs and rough edges more than the golden paths do.
